# Phase 6D.4: bounded Ecommerce lifecycle foundation

Authorized baseline: `7e35b477871ba378cf28c3320581a3cf53b98666`.

This implements the approved design addendum as three explicit traces, with at
most two projects, injected in-memory Storage 7, a controlled Date clock and a
controlled duplicate UUID. It adds no production transition engine or policy.
The initial run has 27 events, 96 applicable contract applications and 7,487
passing primitive comparisons. These are comparisons, not 7,487 Vitest cases.
There are 46 Vitest cases: 27 checkpoints, five metadata/characterization/scope/
purity/reporting controls, and 14 oracle-sensitivity cases.

## Independent inputs and expectations

- `fixtures.ts` transcribes I, C, E, R, A/B/M, T0–T17, the 19 document paths and
  12 checklist IDs literally from the approved addendum. E uses `keyboard-first`.
  It imports only a production TypeScript type, erased at runtime. It does not
  use the Rose & Paw helper, required-field registries, validators or blockers
  to fill the fixture. Unspecified intake values must remain empty.
- Every business choice, `Approved:` prefix, asset, repository path, command and
  manual confirmation is fictional test data. No real client or release
  approval is asserted. Nothing runs the fictional target commands or services.
- `expectations.ts` authors stored status, display status, overall review label,
  source data, flags, timestamp, count, readiness, active identity, archive
  membership, operation result and write budget separately at every checkpoint.
  Its small helpers abbreviate literal rows; they have no production runtime
  imports and do not calculate status or readiness.
- `observe.ts` reads raw serialized status/review labels and separately observes
  existing selectors, Client Review and package readiness. Observations cannot
  grant authority. Its adapter throws before changing its map in C7.
- `contract.ts` is a pure comparator. No production selector, validator,
  repository, parser or readiness API is imported at runtime. Expectations never
  come from a production result or a regenerated snapshot.
- D0/D1/D2 are captured copies of earlier generated bytes used only for the
  independently specified retention law. They do not supply expected readiness,
  counts, paths, statuses or timestamps. The 19 paths, nonblank/missing-marker
  conditions and readiness expectations are independently authored.
- `traces.ts` calls existing APIs in the approved order. It does not read the
  expectation table to choose inputs or operations.

## Preservation and sensitivity

Every observation verifies that its own read leaves serialized bytes unchanged.
A2/A7g/A10g, B4 and C0–C8 additionally verify operation-level byte preservation.
Named source/confirmation mutations retain the specified prior document bytes.
Successful writes are checked through explicit field frames, not whole-record
byte equality.

Ecommerce source-review cards refresh calculated `updatedAt` during reads; a
later successful write can persist that projection for both records. This is
characterized separately: B0/B1 persist the current card times; B4 retains T14
in raw bytes while observing T15 in the calculated cards. Project timestamps,
canonical source answers and manual flags remain separately protected.

Fourteen sensitivity controls first accept the correct observation, then reject
one deliberate corruption: unrelated source edit, resurrected timestamp, changed
retained output, premature stored/display/Client Review/package readiness,
changed overall review label, missing confirmation, wrong file count, inherited
duplicate package, lost archive flags, wrong fallback and changed failed-write
bytes. The original observations are retained and the oracle is reproducible.

## Explicit limits

No global terminal/backward-transition rule, archive editing lock, no-op or
generic-update invalidation policy is introduced. Legacy/manual statuses remain
characterization only. The initial trace does not cover last-active-to-null,
fallback ties, repeated archive/restore, archived editing/opening, direct review
item N/A/deferral changes, CR-ready/content-blocked corruption scenarios,
migrations, quarantine, concurrent writes, failed creation or unavailable reads.
Existing regression suites remain responsible for their existing cases.

Canvas record lifecycle, Planning/Controlled Apply, confirmation provenance,
arbitrary exploration, package coherence, fuzzing and Core extraction remain
outside this foundation. Preview blocker counting and Ecommerce `launchReady`
findings remain open; no new assertion or remediation of those policies occurs.
No production source, Storage behavior, dependencies, CI, UI or public API is
changed. Merge and Phase 6D.5 require separate Architect authorization.
